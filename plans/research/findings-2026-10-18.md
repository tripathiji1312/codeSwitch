### [CORRECTNESS-01] Parler verification branch always throws; every demo CB0-acceptance number is computed against `torch.randn`
**Evidence**
- `codeswitch_tts/engine/speculative_engine.py:246-266`:
  ```python
  full_seq = torch.cat([prefix_tokens, draft_tokens], dim=1)          # (1, 1+K)
  ...
  if self.backend == "indic_parler_tts":
      try:
          decoder_outputs = self.ar_model.decoder(input_ids=full_seq, return_dict=True)
          hidden = decoder_outputs.last_hidden_state                # line 256
          logits = self.ar_model.decoder.lm_heads[0](hidden)        # line 257
          draft_logits = logits[:, -draft_len:, :]
      except Exception:
          draft_logits = torch.randn(b, draft_len, 1024, device=self.device)   # line 260
  ```
- Runtime parler-tts is GitHub **main** (notebook cell 6 `pip install -q -U git+https://github.com/huggingface/parler-tts.git`; `KAGGLE_RUN.md:66`). In main: `ForConditionalGeneration.decoder = ParlerTTSForCausalLM` (`ptts.py:2360`), whose forward runs the inner decoder that starts with `input = input_ids.reshape(-1, self.num_codebooks, input_ids.shape[-1])` (`ptts.py:1423`). For any non-empty `(1, 1+K)` that reshape requires `1/9` to be an integer → **always raises**. Executed check (movio/.venv, torch 2.13.0+cu130): `torch.zeros(1,7).reshape(-1,9,7)` → `RuntimeError: shape '[-1, 9, 7]' is invalid for input of size 7`.
- Even if the reshape passed: `ParlerTTSForCausalLM` returns `ParlerTTSCausalLMOutputWithCrossAttentions` (`ptts.py:1885`; fields at 197–203 are `loss/logits/past_key_values/hidden_states/attentions/cross_attentions/per_codebook_losses`) — there is **no `last_hidden_state`** on it (that attribute exists only on the inner decoder's `BaseModelOutputWithPastAndCrossAttentions`, `ptts.py:1650,1811-1817`), so line 256 raises `AttributeError`. The branch is unreachable-as-written; the bare `except Exception` silently converts both failures to uniform random logits, which then drive `F.softmax` (264–265) and the acceptance loop (305–334).
- Call sites/consumers: Mode A `streaming_pipeline.py:184-190` → `cb0_acceptance_rate=verif_res.acceptance_rate` (208) and 295/348; notebook cell 10 prints `CB0 Acceptance: {result.cb0_acceptance_rate:.1f}%`.
- Mode A also passes no prefix → `prefix_tokens = torch.zeros((batch_size, 1), ...)` (`speculative_engine.py:288-289`), so even a repaired forward would be conditioned on a null prefix.
- The unit test exercises only the other branch: `tests/test_codeswitch_tts.py:76-84` (`backend == "standalone_ar"`, line 262 path).

**Impact** — The verifier — the paper's core mechanism — reports coin-flip acceptance in every `ChunkedStreamingPipeline` run (the notebook demo path), and the swallowing `except` guarantees this stays invisible. The evaluation suite (`run_full_evaluation.py`) uses its own `TeacherForcedScorer` (521–553) + `rejection_sample` (601–628), so Table I/IV/V CB0 numbers are *not* affected by this bug — the demo path is.
**Effort** M — **Risk** LOW-MED — **Confidence** HIGH
**Fix sketch** — Feed the decoder the row layout it expects (`(K, L)` with bos rows, as the working scorer does at `run_full_evaluation.py:526-530`), pass `encoder_hidden_states` (+ `prompt_hidden_states`/mask when `not prompt_cross_attention`), read `out.logits[0]`, slice codebook 0; replace `except Exception:` with a logged re-raise (or a clearly flagged "unavailable" state) so interface drift cannot silently randomize metrics.

**Evidence**

- Notebook: cell 0 markdown claims the pipeline "**achieves <300ms Time-To-First-Audio (TTFA)**"; cell 10 prints `TTFA (ms): {result.ttfa_ms:.1f} ms  (Target: <300 ms)`; cell 12 prints the benchmark table and, after a design-targets box, tells the reader to "quote the measured TTFA … from the table above". Cell 8 constructs `CodeSwitchTTSConfig()` with no override, and cell 6 installs parler → on Kaggle with Parler loaded this is Mode A.
- Contrast: the evaluation path measures honestly — `ttfa_e2e_ms = ready_ms` (wall clock, `run_full_evaluation.py:1033-1035`) and Table I's caption distinguishes "TTFA-c: component compute latency; TTFA-e2e: wall-clock to first audio buffer" (2592). **Impact** — The notebook's headline latency claim is not derivable from the code: the printed value is ≈ `draft_ms + verify_ms + 40.5 ms` regardless of how slow the real first-audio moment was (that moment is ≥ `gen_time_ms`, seconds on T4). **Effort** M — **Risk** MED — **Confidence** HIGH
**Fix sketch** — Either report `ttfa_ms = gen_time_ms + draft_ms + verify_ms` (+ any measured first-chunk work) for Mode A and stop calling it streaming TTFA, or implement genuine incremental generation; replace the 22.5/18.0 constants with measured times; keep chunk>0 latency in `chunk_latency_ms` only.

### [CORRECTNESS-03] Residual training windows drop every shard’s trailing partial window (up to ~50 % of frames)
**Evidence** — `train_draft_distill.py:859` (`WINDOW = 86  # ~1 s of DAC frames`) and 907-920:
```python
for start in range(0, max(1, t - self.WINDOW + 1), self.WINDOW):   # line 913
    end = min(start + self.WINDOW, t)                              # line 914
    if end - start < 24:                                           # line 915
        continue
```
Arithmetic: for shard length `t ≥ 86` the starts are `0, 86, …, 86·floor(t/86) − 86`, so coverage is `86·floor(t/86)` and the last `t mod 86` frames are **never windowed** (t=100 → frames 86-99 dropped; t=140 → 54/140 = 38.6 % dropped; t=171 → 85/171 = 49.7 % dropped). The `< 24` guard only fires for shards shorter than 24 frames; `end = min(start + self.WINDOW, t)` shows truncated tail windows were intended to be kept, so the guard is effectively dead for its purpose. Only the window count is logged (1006-1008), never the dropped-frame count.
**Impact** — The residual decoder (the component that makes CB0-only verification viable, per `PAPER_CLAIMS_AND_EVIDENCE.md` §2) never trains on the final ≤1 s of each training utterance; up to half of a shard’s frames can be silently excluded.
**Effort** S — **Risk** LOW — **Confidence** HIGH
**Fix sketch** — `for start in range(0, t, self.WINDOW):` (then line 915 does what it says); log dropped frames per run.

### [CORRECTNESS-06] High-pass filter guard is below scipy’s padlen — 12–15-sample inputs raise instead of passing
**Evidence** — `codeswitch_tts/utils/audio.py:36-39`:
```python

Executed check (movio/.venv, scipy 1.17.1): `scipy.signal.sosfiltfilt(scipy.signal.butter(4, 60.0, btype="highpass", fs=44100, output="sos"), np.zeros(n))` raises `ValueError: The length of the input vector x must be greater than padlen, which is 15.` for every n in 8…15 and succeeds at n=16. ### [CORRECTNESS-07] `switch_distances` sentinel contradicts its docstring — pre-first-switch frames land in low buckets, not “16+”

### [CORRECTNESS-09] Overlap crossfade is applied to already-contiguous chunks (content deleted, comb at joins)
**Evidence** — `codeswitch_tts/utils/audio.py:43-59`:
```python
tail = chunk1[-crossfade_samples:] * fade_out + chunk2[:crossfade_samples] * fade_in   # 55
chunk1_trimmed = chunk1[:-crossfade_samples]                                            # 56
chunk2_trimmed = chunk2[crossfade_samples:]                                             # 57
blended = np.concatenate([chunk1_trimmed, tail, chunk2_trimmed])                        # 58
```
Callers pass *consecutive slices of one waveform*: `streaming_pipeline.py:169-172` (`chunk_audio = authentic_audio[start_sample:end_sample]`) then 317-326 crossfade them; `run_full_evaluation.py:1041-1048` does the same for its chunk waves. For contiguous inputs the join re-mixes samples 256 apart (comb spacing ≈ 44100/256 ≈ 172 Hz) and deletes `crossfade_samples` = 256 samples (≈5.8 ms at 44.1 kHz) of real audio per boundary — 0.58 % of every 1 s chunk. `tests/test_codeswitch_tts.py:90-92` asserts the shortened length, locking the behavior in.
**Impact** — Small per-boundary losses/coloration in every streamed utterance, contradicting the "seam-free"/contiguous-chunk intent; if overlap-crossfade is the intended API, the callers are wrong to pass non-overlapping slices, and vice versa.
**Effort** S — **Risk** LOW-MED — **Confidence** HIGH (mechanism) / MED (bug-vs-intent)
