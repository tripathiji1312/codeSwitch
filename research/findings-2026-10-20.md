### 2026-10-20 — Is `parler_model.audio_encoder` the correct 44.1 kHz DAC decoder?

**Subagent question:** Is the claim "Parler-TTS already contains the exact pretrained 44.1kHz DAC decoder in memory as `parler_model.audio_encoder`; bind DACWrapper directly to `parler_model.audio_encoder`" technically correct for `ai4bharat/indic-parler-tts` (and the `parler-tts` package version used by this repo)? Specifically:
- What is the class of `ParlerTTSForConditionalGeneration.audio_encoder` in current `huggingface/parler-tts` source?
- Does that object expose a `decode(audio_codes=..., audio_scales=...)` method that accepts 9-codebook `(B,9,T)` codes and returns 44.1kHz audio? Or is it encoder-only / a different wrapper?
- Is it loaded with pretrained weights by `from_pretrained`, or is it a separately downloaded codec?
- What is the correct input layout and output shape? Are there known `frame_rate`, `sampling_rate`, `hop_length`, or `audio_scales` pitfalls?
- Does the code in this repo already use this object correctly in `run_full_evaluation.py::_decode_codes` and `train_draft_distill.py`?
- Is there any reason `DacModel.from_pretrained("ylacombe/dac_44khZ_8kbps")` fails under transformers 5.16.1, and would using `parler_model.audio_encoder` avoid that failure?

**Answer:**

The claim is **half right and half wrong** — the operational conclusion (bind the repo's `DACWrapper` to `parler_model.audio_encoder`) is technically sound for `ai4bharat/indic-parler-tts` under the transformers versions this repo actually uses (Kaggle pin **4.46.1**, local **5.16.1**), but the mechanism as stated is wrong for that checkpoint:

1. **Class.** For `ai4bharat/indic-parler-tts` with parler-tts 0.2.x and transformers > 4.44.2dev, `ParlerTTSForConditionalGeneration.audio_encoder` is **`transformers.models.dac.modeling_dac.DacModel`** — *not* parler-tts's own `parler_tts.dac_wrapper.DACModel` (there is no class named `DACWrapper` anywhere in parler-tts; `DACWrapper` is this repo's own class at `codeswitch_tts/utils/audio.py:90`). The class is decided by the checkpoint's nested `audio_encoder.model_type: "dac"` plus the version guard in `ParlerTTSConfig.__init__` (the guard only rewrites `"dac"` → `"dac_on_the_hub"` when the checkpoint's top-level `transformers_version` is ≤ `4.44.2dev`; indic says `4.46.0.dev0`, so no rewrite).
2. **Decode signature.** The stated `decode(audio_codes=..., audio_scales=...)` is the **parler-wrapper** signature (`dac_wrapper/…/modeling_dac.py`: `def decode(self, audio_codes, audio_scales, padding_mask=None, return_dict=None)`, `audio_scales` required, 4-D `(1, B, K, T)` codes). The object actually in `indic-parler-tts` has **`DacModel.decode(self, quantized_representation=None, audio_codes=None, return_dict=None)`** — **no `audio_scales` keyword at all** (TypeError), and it takes 3-D **`(batch, 9, T)`** codes, returning `DacDecoderOutput.audio_values` of shape `(B, T × 512)` — i.e. 44.1 kHz audio (T frames at hop 512, config `sampling_rate: 44100`). So "accepts 9-codebook (B,9,T) and returns 44.1 kHz" is true; "via `audio_scales`" is false for indic. It is **not encoder-only** — it is the full encoder+quantizer+decoder, and the pretrained decoder weights *are* in memory.
3. **Pretrained weights, in-memory.** Yes, loaded by the composite `from_pretrained` from the same `model.safetensors` (the checkpoint contains `audio_encoder.*` tensors; 223/223 names and shapes match a freshly instantiated `DacModel`, and I verified several tensors are **byte-identical** to `ylacombe/dac_44khz`, e.g. the 44,040,192-byte `decoder.conv1.weight` and all `quantizer.quantizers.*` samples checked). The audio encoder is frozen during training (`freeze_encoders`, `modeling_parler_tts.py:3311-3319`), which is why the values are unchanged. Not a separate download at inference time.
4. **The repo's own code.** `run_full_evaluation.py::_decode_codes` (lines 659-695) and `train_draft_distill.py::_decode_codes_for_validation` (lines 309-341) both try 3-D/4-D × with-scales/without-scales, so they **work correctly** (for transformers `DacModel` the with-`audio_scales` attempts always TypeError and the 3-D no-scales attempt succeeds). `streaming_pipeline.py:106-107` already binds the parler audio encoder into `AudioProcessor`/`DACWrapper` (`model=` → backend `"passed_model"`), and `DACWrapper.decode`'s first attempt `self.model.decode(audio_codes=(B,9,T))` is exactly right for transformers `DacModel`. `train_draft_distill.py::_codec_reencode` uses `audio_encoder.encode(wave)` correctly (exists in both 4.46.1 and 5.16.1).
5. **`DacModel.from_pretrained("ylacombe/dac_44khZ_8kbps")` failure.** It fails under **both** 5.16.1 *and* the repo's Kaggle pin 4.46.1 — verified live in an isolated transformers-4.46.1 venv: `AttributeError: property 'frame_rate' of 'DacConfig' object has no setter` ("Can't set frame_rate with value 86"), because that repo's 2024-04-10 config is the old parler-dac_wrapper format (`"frame_rate": 86`, no `sampling_rate`) while `DacConfig.frame_rate` is a read-only property since transformers 4.44. Additionally its weights are in the wrapper layout (`model.decoder.*`, 301 tensors) and could never load into `transformers.DacModel` (`decoder/encoder/quantizer.*`, 223 tensors). Using `parler_model.audio_encoder` avoids this entirely (its config has no `frame_rate` key and its weights are the right layout). **Note:** in the repo's `_load_dac`, this failure is swallowed and silently downgraded to a randomly-initialised `DacModel(cfg)` (`audio.py:128-138`), which is the "B/C noise" class of bug — so the claim's practical motivation is real.

### 2026-10-20 — Exact argmax/sampling patch surface for Configs B/C

**Subagent question:** What is the exact code surface needed to run Configs B and C with greedy/argmax decoding instead of sampling, for both the draft CB0 model and the residual CB1-8 model? Verify:
- `DraftTransformer.forward` supports `sample`; does `generate_chunk` expose/pass it? Quote the signature and call.
- `ResidualDecoder.forward` default `sample=False`; what does the evaluator pass at `run_full_evaluation.py` around the residual call?
- Every production/eval/diagnostic call site that currently samples (`sample=True`, omitted `sample`, `do_sample=True`, `temperature=1.0`) and whether it affects B/C audio.
- Whether `temperature=0.0` is a valid way to request argmax in these classes, or whether the code would divide by `max(temperature,1e-5)` and still sample.
- Any test that asserts the current default/behavior and would need updating.
- A minimal, exact patch list (file:line, old snippet -> new snippet) for adding a `--sample-mode` or equivalent, but do not edit.

**Answer:**

The complete eval-time sampling surface for Configs B/C is exactly **two calls** in `run_full_evaluation.py` plus **one missing kwarg** in `DraftTransformer.generate_chunk`:

1. **Draft CB0** — `EvalSynthesizer._chunked_synthesis` calls `self.draft.generate_chunk(text=normalized, num_frames=n_frames, temperature=1.0, device=self.device)` (run_full_evaluation.py:927-929). `generate_chunk` **does not expose `sample`**, so it always lands on `forward`'s default `sample=True` → `torch.multinomial`. To flip CB0 to greedy you must first add `sample` to `generate_chunk` and forward it.
2. **Residual CB1-8** — the evaluator calls `self.residual(cb0_tokens=..., temperature=1.0, sample=True)` (run_full_evaluation.py:1003-1007). `ResidualDecoder.forward` already accepts `sample` and defaults to `False`, so the evaluator is *explicitly overriding* the argmax default; only this one argument needs to change.
3. **`temperature=0.0` is NOT a valid argmax request** in either class: both divide by `max(temperature, 1e-5)` (`draft_transformer.py:199`, `residual_decoder.py:136`) and the `if sample:` branch still calls `torch.multinomial`; only the boolean `sample` selects `torch.argmax`. Also, B/C temperature is hard-coded `1.0` at all three sites; there is no temperature CLI.

A minimal patch is: add `sample: bool = True` to `generate_chunk` (signature + forwarded call), add `--sample-mode {sample,argmax}` to `build_arg_parser`, read it via `getattr(self.args, "sample_mode", "sample")` inside `_chunked_synthesis`, and pass it to both the draft and residual calls. No test currently asserts the sampling default, but `test_synth_C_falls_back_below_threshold` monkeypatches `_chunked_synthesis` with a fixed 4-argument signature — so the mode must be read from `self.args`, not added as a function parameter.

Caveat needing a decision (not code-fixable by the flag alone): Config C feeds the (now greedy) draft tokens into `rejection_sample(q_true, chunk_probs, chunk_tokens, rng_accept)` (run_full_evaluation.py:971), which assumes the proposal tokens were *drawn from* `chunk_probs`; with argmax tokens the math is a top-1-proposal variant and C remains stochastic (seeded `np.random.RandomState(seed)` at line 917). Config B becomes fully deterministic per utterance.

### 2026-10-20 — What `train_draft_distill.py` actually trains and why B/C are noise

**Answer:**

**What `train_draft_distill.py` actually trains** (all verified in-file):

1. **Teacher pass** — `SpeculativeEngine` (Indic Parler-TTS) synthesizes the corpus sentence-by-sentence; the 9-codebook DAC token stream is captured (`--target-source auto|lm|codec`; LM capture is validated **once**, on sentence 0, by decoding the captured codes and correlating with the returned waveform, `train_draft_distill.py:450-486`; fallback = DAC re-encode of the waveform, `:490-523`). Each sentence becomes a shard file `teacher_cache/shard_<sha1(norm_text)[:16]>.npz` (`:190-199`) containing `index, raw_text, norm_text, n_chars, frames, codes(9,T) int16, audio_sec, target_source, gen_ms` (`:202-243`). Frames are trimmed to those where *every* codebook holds a valid token and capped at 430 (`:391-403`).
2. **Draft** — `DraftTransformer` (`CharacterTokenizer` vocab 4096; 4-layer 512-d encoder, d_ff 2048, 8 heads; `TemporalLengthProjector` = `F.interpolate(text_len → num_frames)` + 2 convs; linear head → 1024 CB0 logits). **16.81 M params** (instantiated in the venv; the module docstring's "~65M" is wrong). Objective: plain CE of teacher **CB0** frames vs text, `AdamW(3e-4, wd .01, betas (.9,.95))`, grad-clip 1.0, fp16 AMP + GradScaler, `ReduceLROnPlateau(factor .5, patience 3)` on val loss, `epochs=80` default (60 in the big-run notebook), `patience=12`, val = every 10th shard (`i % 10 == 9`), reported metric = teacher-forced top-1/top-5 (`:674-852`).
3. **Residual** — `ResidualDecoder` (d_model 384; 4 dilated blocks k=5, dilations 1/2/4/8; 8 parallel Conv1d heads → CB1-8). **7.10 M params.** Windows of exactly 86 frames (`WINDOW=86`, `:860`), trailing window right-aligned (`:908-938`); **input = teacher CB0** (`s.codes[0]`, `sched_p` replaces it with *draft* CB0 when scheduled sampling is on, `:940-962`), **target = teacher CB1-8**; loss = mean of 8 CEs (`:977-985`); same optimizer/LR/patience; `epochs=60` default; sched ramp `target·(epoch-1)/(epochs-1)` (`:1056`). Draft CB0 for scheduled sampling is precomputed in memory, one sampled NAR pass per shard at the teacher's frame count (`:883-906`).
4. **Length model** — least-squares chars→frames over the teacher set, clamped to `[0.6·min, 1.25·max]` observed frames (`:136-173`), written into `meta.json`; eval uses it for frame sizing (`run_full_evaluation.py:729-732`).
5. Checkpoints (`state_dict + config + meta`) to `codeswitch_ckpt/{draft_cb0.pt, residual_cb1_8.pt}` **after both stages**, plus `meta.json`, plus a sanity WAV (`:1336-1404`).

**Prioritized causal list for the B/C noise** (most likely first; all "config B/C = Draft+Residual, unverified draft CB0 → residual fill" per `run_full_evaluation.py:130-134, 900-1014`):

1. **The trained draft's CB0 is intrinsically wrong ~92 % of frames, and B/C emit it unverified.** Measured: `CB0 top-1 7.78 % / top-5 22.61 %` (300-sentence ckpts, `PAPER_CLAIMS_AND_EVIDENCE.md:6`), `7.45 % ≈ 76× chance` for the 2k run (`plans/README.md:84-85`); the shipped residual's mean CB1-8 top-1 is **0.11 % ≈ chance** (`PAPER_CLAIMS:42`), and B/C CER medians are 94.0 / 98.6 % (`:23`). Config B uses the *sampled* draft CB0 (`generate_chunk(..., temperature=1.0)` → `sample=True`, `run_full_evaluation.py:927-929`) and the residual is conditioned **only** on CB0 (`residual_decoder.py:92-98`) with no text/verification — 93 % wrong coarse codes *is* noise. *Change:* don't ship B/C from a 7 %-CB0 draft; either (a) raise CB0 accuracy (items 2-3), (b) train the residual conditioned on the **draft's** CB0 distribution, or (c) report B/C with CB0 argmax + gate as the headline and treat raw NAR as the ablation.
2. **Draft training conditions every sample on `num_frames = batch max frames`, while the per-sample target is its own teacher frame sequence → systematic text↔frame misalignment** (`_collate` `:693-697`, forward `num_frames=max_t` `:721-731`, top-k eval also uses `max_t` `:749-771`). Only the longest sample in each batch is supervised consistently; everything shorter is trained with the text stretched over `max_t` frames, so at deployment (one sample, `num_frames` = its own length, `run_full_evaluation.py:906-929`) the model's learned text→time mapping is a smear. **Controlled experiment I ran with the repo's own `DraftTrainer` code** (tiny CPU model, 25 epochs, fabricated *learnable* echo target): stock batch-max **18.35 %** deployment top-1 / val 3.64, per-sample frames **91.88 %** / val 0.35. *Change:* bucket batches by frame count (or one forward per length); assert `loss` is only computed where `num_frames == t_i`.
3. **The teacher target is a single sampled sequence per sentence with a loose, forced length prior.** `do_sample=True, temperature=1.0`, `min_new_tokens = 0.7×86.13×len/13`, `max_new_tokens = 1.8×… + 30` (`:416-419, 428-436`): the LM is forced to keep emitting at least 70 % of a 13-chars/s estimate and is cut at 1.8×, so shards can contain force-extended tails / truncations that the NAR draft is then trained to reproduce; a NAR CE against *one* sample can only approximate the batch-mean token (`best val ≈ 5.11` vs uniform 6.93 is exactly a smoothed target). *Change:* capture K samples per sentence and train against their empirical distribution (or KD with teacher top-k probs — the streamer only keeps ids today, `:246-306`), tighten the length prior, and/or lower the capture temperature.
4. **Residual exposure bias, and the 0.5 scheduled sampling runs *toward* a 7 %-accurate draft as the training signal.** Default is `--residual-sched 0.0` → trained on clean teacher CB0 but deployed on draft CB0 (`:877-881, 949-953`, `KAGGLE_RUN.md:169-173`). The big-run fix (`--residual-sched 0.5`) then conditions ~half the windows on mostly-wrong draft CB0 while the targets remain *teacher* CB1-8 — the model cannot tell clean from noisy input, so it hedges toward the marginal. Also: the ramp is over *configured* epochs (60), and with `--skip-draft` (resume) the draft is silently dropped (`draft_model=None`, `:1331`) so sched is off with only an info print (`:1051-1054`). *Change:* freeze the draft, train the residual on **100 % draft CB0**, ramp per optimizer step, and re-check with `diagnose_audio_bug.py` `rt_*` vs `rd_*`.
5. **Budget/steps: the runs stopped at the *epoch* caps, not the wall-clock caps — for these model sizes that is the binding constraint.** With 2000 shards, a draft epoch is exactly `ceil(1800/24) = 75` optimizer steps, so 60 epochs = 4500 steps; 5.5 min ⇒ ≈5.5 s/epoch ≈ 73 ms/step, i.e. `--max-minutes 30` was never reached (residual: 60 epochs at ~190-220 steps/epoch ≈ 12 k steps; 8.9 min ≈ 8.9 s/epoch, `--max-minutes-residual 20` never reached) — an *inference* from the arithmetic, no logs exist locally. ### 2026-10-20 — Is the Medusa / "let Parler generate CB1-8 from CB0" pivot valid?

**Subagent question:** Is the other AI's proposed architectural pivot technically valid: "keep Indic Parler-TTS frozen; add Medusa-style lookahead heads to Parler decoder layers; Parler already has 9 pretrained LM heads, so pass Codebook 0 to Parler and let Parler generate Codebooks 1-8 in a single parallel teacher-forced forward pass"? Specifically verify:
- How Parler-TTS represents the 9 codebooks and whether CB1-8 can be produced in one parallel pass from CB0 alone (delay pattern, causal masking, `input_ids` layout, `logits` shape).
- Whether Parler's decoder hidden states are accessible for Medusa heads and what the actual generation loop is.
- Whether the claim "Parler already aligned Tamil text to speech frames" is supported by the model architecture/training, or overstated.
- What a realistic Medusa/self-speculative implementation would require in this repo (`codeswitch_tts/engine/speculative_engine.py`, `run_full_evaluation.py`), and whether it is a smaller or larger change than fixing the existing student.
- Any published 2025-2026 work on speculative decoding for codec TTS that directly supports/contradicts the claim; cite exact papers/URLs.

**Answer:**

**Verdict summary — the proposed pivot is technically invalid as stated, but contains one true observation and one precedent-supported component.**

- **Sub-claim A — "Parler already has 9 pretrained LM heads": PARTLY TRUE (misleading for the v1.1 family).** Parler's decoder head is `self.lm_heads`, created either as a `nn.ModuleList` of 9 `Linear(hidden, vocab)` (one per codebook) **or** as a single fused `Linear(hidden, vocab*num_codebooks)` when `use_fused_lm_heads` is set — the public `parler-tts-mini-v1.1` config sets `"use_fused_lm_heads": true`. Indic Parler-TTS is a fine-tune of `indic-parler-tts-pretrained`, itself built on mini-v1.1 (model card), so likely fused heads; its own `config.json` is gated (401), so this specific checkpoint is **not verified**.

- **Sub-claim B — "pass Codebook 0 to Parler and let Parler generate Codebooks 1–8 in a single parallel teacher-forced forward pass": INVALID as stated.** Three independent, code-verifiable blockers:
  1. **The delay pattern means one column's 9 head outputs are 9 *different frames*, not 9 codebooks of one frame.** Heads at grid column *c* predict frame `c-1-k` for codebook *k*. The 9 codebooks of a given frame *f* land in 9 successive columns (`f+1 … f+9`). This is why upstream documents "1720 decoding steps to generate 20 seconds of audio" (~86 Hz ⇒ ~1 step per frame) — it is already one *frame* per step, not nine.
  2. **The decoder input at each column is the *sum* of all 9 codebook embeddings** (`inputs_embeds = sum([...])`). A CB0-only pass leaves 8 of the 9 embedding terms of every column undefined. Teacher-forcing the delayed grid requires the CB1–8 tokens of earlier frames — i.e., exactly the tokens you are trying to generate. Substituting BOS (what this repo already does for scoring) is an out-of-distribution input layout, not the model's trained conditional.
  3. **Causal masking forbids same-column cross-codebook prediction**, and the model's own generation path (`prepare_inputs_for_generation` → `GenerationMixin._sample`) appends one token *per row per step*, so the AR-consistent way to obtain CB1–8 of one frame costs 9 successive steps. There is no single-pass shortcut from CB0 alone.
  
  **What *is* true and useful (a corrected version of the claim):** a **teacher-forced forward over the full `(batch*9, L)` grid returns logits for all 9 codebooks × all positions in one pass** (`lm_logits.reshape(-1, *shape[2:])`); so *verifying* CB1–8 candidates for all frames does cost one target forward — this matches the repo's own `PAPER_CLAIMS_AND_EVIDENCE.md` §2 observation ("teacher-forced forward computes logits for all 9 rows; scoring CB0 costs the same forward as scoring all 9"). The pivot therefore conflates **scoring/verification** (one pass, correct) with **generation** (needs the diagonal, ~1 step/frame, AR-consistent only if the other rows carry the model's own earlier outputs).

- **Sub-claim C — "Parler already aligned Tamil text to speech frames": OVERSTATED if read as explicit alignment; SUPPORTED as "trained to map Tamil text to DAC codec frames."** Tamil is an officially supported language with a recommended speaker (Jaya) and Indic Parler-TTS was fine-tuned with a Tamil subset (52.25 h / 29,204 utts in the released fine-tune table), on the Rasmalai dataset/recipe (13,000 h, 23 languages). There is no forced-alignment mechanism in the architecture: Tamil text enters via a prompt tokenizer and is concatenated to decoder inputs as `prompt_hidden_states` (or cross-attended when `prompt_cross_attention=True`); text→frame mapping is learned autoregressively. This repo's own teacher pipeline already exploits it: it calls `ar.generate(...)` on Tamil/Tanglish text and captures the 9-codebook DAC stream as distillation targets.

- **Sub-claim D — realistic Medusa implementation in *this* repo: LARGER than fixing the existing student, by a wide margin.** Requirements and why: (1) fork/override Parler's `generate` → inherited HF `_sample` (Parler defines no `_sample`; it calls `self._sample`), re-implement the stateful delay-pattern mask, the per-codebook EOS `ParlerTTSLogitsProcessor`, the tree/draft-column sampler and the final `(b, 9, T)` reassembly; (2) Medusa heads on the last hidden state (`output_hidden_states=True`) — note a "future column" is 9 tokens spread across 9 frames, so each head must emit 9 codec distributions (or ~45 heads for 5 offsets) versus one vocab per head in LLMs; (3) new training over the teacher cache + Parler hidden states (teacher capture is the known bottleneck, ~10 s/sentence on T4); (4) entirely new acceptance/telemetry in `run_full_evaluation.py` (its `rejection_sample` assumes a single 1-D token stream; the current `SpeculativeEngine` Parler branch is already dead code that silently returns `torch.randn`). By contrast, "fixing the existing student" is: corpus scale + two training flags + already-identified bug fixes in `train_draft_distill.py`, runnable end-to-end today.

- **Sub-claim E — published 2025-26 prior art: supports Medusa-style heads for codec-TTS AR streams (single-stream), does NOT support the CB0→CB1-8 single-pass idea, and no work was found on Medusa/lookahead for delay-pattern multi-codebook LMs (MusicGen/Parler).** See Evidence for exact papers; VADUSA (ICASSP 2025) is the closest precedent and it explicitly warns that with 8-codebook EnCodec tokens acceptance collapses (1.85× vs 2.94× for semantic tokens).
